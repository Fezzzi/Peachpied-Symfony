\section{Compiling Symfony Components}
The process of Symfony Components compilation can be easily tested on a small set of Symfony Components that are required by the very basic Symfony application called Symfony Skeleton. Additionally, Twig template engine Components with their dependencies can be counted in as well. These Components with required source code edits and a Component-specific build configuration prepared are included as a part of the repository and can be found in the \texttt{Peachpied.Symfony/Components/4.2.3/vendor} directory.

Precompiled tools that take care of the compilation are included as a part of the project inside the \texttt{Libs} directory but they might require recompilation due to the possible differences in the operating systems and the CPU architectures. To test this, simply run the \noindent\codebox{./Peachpied.Symfony.BuildGen.exe \\ --project ../Peachpied.Symfony/Components/4.2.3} command from the \texttt{Libs} directory. In case of success, a set of \texttt{.msbuildproj} files will be generated inside the provided working directory, one for each Symfony Component installed there. The script will also produce the \texttt{buildScript.ps1} script inside the \texttt{Libs} directory. In case the script execution fails, the tools might require recompilation because of differences in architectures of computer it was compiled on and the one it is now executed on. To do so, clear the content of the \texttt{Libs} directory and execute \texttt{dotnet publish -r [Runtime]} from the \texttt{Tools/BuildGen} directory of the repository. The \texttt{[Runtime]} parameter is to be replaced with custom .NET Core Runtime Identifier. For the table of available values refer to the Microsoft .NET Core guide. The Runtime Identifier used for the tools compilation is \texttt{win10-x64}.

To perform the actual compilation execute \texttt{Libs/buildScript.ps1} generated before. Alternatively, the whole compilation process can be achieved by running: \noindent\codebox{./Peachpied.Symfony.BuildGen.exe \\ --project ../Peachpied.Symfony/Components/4.2.3 \\ --build} from the \texttt{Libs} directory. The additional \texttt{--build} flag tells the tool to automatically execute \texttt{buildScript.ps1} after build files are generated, making it possible to compile all the Components with a single command. Running this command should output 35 NuGet packages into the \texttt{Nuget-Repository/Components} directory, corresponding to the 35 Symfony Components compiled. We have precompiled these packages and included them as a part of the project repository. 

\paragraph{Custom Components Compilation}
Following instruction focuses on describing how to compile custom Symfony Components of different versions than those provided with the repository from the downloaded sources. This process will most probably require to manually modify downloaded sources and might even require further cooperation with the Peachpie development team in order to resolve all the compilation errors. This guide is therefore suited for users with a deeper understanding of MSBuild and a greater passion for the subject as we can provide no manual that describes how to resolve all possible compilation errors. 

First of all, it is necessary to get the actual Symfony Components. This is done by using Composer, PHP package manager, and thus requires having both PHP and Composer installed. Prior to any Symfony Component downloading, we have to initialize the working directory as a project. This is done by running the \noindent\codebox{composer init} command and following the interactive process, and results in creation of the \texttt{composer.json} file. Values set for the project name, authors, etc. during the interactive mode are of no concern as our compilation process does not pay any attention to them. Alternatively, an empty \texttt{composer.json} file with just \texttt{\{\}} as its content will work the same. Finally, each Component that is to be compiled can be downloaded using the \noindent\codebox{composer require [Component name](:[version])} command. This will further update the \texttt{composer.json} file as well as produce the \texttt{composer.lock} file with detailed information about each Component downloaded. The presence of both these files within the working directory is mandatory for any further progress.

When Symfony Components are in place, we can perform compilation in a way mentioned in the previous paragraph. The only modification required is to provide custom relative path to the working directory as an argument to the \texttt{--project} parameter. 

The next step consists of repetitive attempts to compile the components and application of required fixes. To trigger Components compilation, run the previously mentioned \texttt{buildScript.ps1}. This will perform sequential compilation of all the Symfony Components while adhering to the required order denoted by the dependency tree. Each compilation error encountered has to be resolved manually either by excluding the whole file from the compilation or by modifying the PHP code to compilable form. To exclude the \texttt{.php} source file, it is necessary to head to the \texttt{libsConfig.json} file and create or modify the entry for the Symfony Component and its precise version. The \texttt{excludes} key of each entry holds a list of files that are to be excluded from the compilation. The \texttt{includes} collection can be then used to override default file exclusions from generated \texttt{.msbuildproj} and enforce their inclusion. Finally with \texttt{ignoredDependencies}, it is possible to resolve circular dependency errors that the dependency resolving mechanism of the \texttt{BuildGen} tool was not able to figure out.

After resolving each and every error, the \texttt{buildScript.ps1} successfully produces NuGet packages on execution and stores them under the \texttt{Nuget-Repository/Components} directory.


\section{Deploying Symfony application}
Using the tools and templates provided, Symfony application deployment on the .NET environment in general was simplified into the following summary.

At this point, we expect that all the required Symfony Components are already accessible as NuGet packages, either from included package repository that can be found under the \texttt{Nuget-Repository} directory of the repository or via the custom Components compilation as discussed in the section before. We also expect the project templates from the \texttt{Peachpied.Symfony.Templates} NuGet package to be installed in advance with the following command: \noindent\codebox{dotnet new -i Nuget-Repository/Peachpied.Symfony.Templates}

\paragraph{New Symfony application} 
First of all, we have to set up two projects, one for .NET Core and the other for Symfony. Thanks to the \texttt{Peachpied.Symfony.Templates} NuGet package, this is as easy as running the \noindent\codebox{dotnet new syskeleton} command. A new solution titled \texttt{Symfony-Skeleton} with two projects - \texttt{Server} and \texttt{Skeleton}, will be generated in the working directory.

The \texttt{Server} directory consists only of a simple set-up for Peachpied Symfony application running on Kestrel. Aside from build configuration, the \texttt{Symfony} directory contains \texttt{.php} sources equal to Symfony Skeleton 4.2.3 project with a basic routing and style-sheets configuration.


\paragraph{Existing Symfony application}
Project creation for an existing Symfony application is the same as for a new one with the only difference in running the \noindent\codebox{dotnet new syemptyproj} command instead of the previously mentioned one. After that, Symfony sources of an existing application can be placed into the \texttt{Symfony} directory of generated solution.

This project template comes with no Symfony Components \texttt{PackageReference} configuration, thus leaving the actual configuration up to the user. The best way to do this is to add references to all the Components listed in the \texttt{require} and \texttt{require-dev} fields of \texttt{composer.json}. Although, not all of the dependencies listed are in fact required for successful compilation. One such example that can be safely omitted from compilation is the \texttt{Symfony/Flex} component.


\paragraph{Extending the application}
In order to use additional Symfony Components to the ones included by the \texttt{Peachpied.Symfony.Skeleton} NuGet package, it is necessary to add a \texttt{PackageRefference} to the particular NuGet package to \texttt{Symfony} project's \texttt{.msbuildproj}. When installing a NuGet package to the project with Visual Studio IDE, this is done automatically. It is also necessary to run the \noindent\codebox{composer require [Component name](:[version])} command in order to update \texttt{composer.json} file that is parsed on project's compilation. As a side effect of this, the Symfony Component will be installed into the \texttt{vendor} directory. Having sources of Symfony Components inside of the \texttt{vendor} directory significantly speeds compilations that perform Symfony cache generating. Symfony cache regenerating can be forced by deleting the \texttt{cache} directory, autoload scripts regenerating by deleting \texttt{vendor/autoload.php} and the \texttt{vendor/composer} folder. It might be necessary to do both after new Symfony Components are included.

In order to further extend the application, arbitrary number of custom routes, controllers and other Symfony ecosystem \texttt{.php} code can be included without the need to modify Symfony's \texttt{.msbuildproj} in any way. Symfony cache generating mechanism also keeps track of changes to Symfony application configuration and handles cache regenerating on build automatically.



\section{Example 1: An application using Symfony and both Twig and Razor template engines}
Usage of the Twig-Razor interoperability features will be demonstrated on the \texttt{Examples/Twig-Razor-Full-Page} application. In order to run this example simply execute the \noindent\codebox{dotnet run} command from the \texttt{Examples/Twig-Razor-Full-Page/Server} directory. Doing this will start the application on \texttt{http://localhost:5004}. The first application start-up may take several minutes because all the Symfony Components need to be unpacked from the NuGet packages and the autoload scripts with cache have to be produced. Any subsequent application start-up completes within several seconds. 

This example shows a possible way of splitting front-end of an application into two distinct parts, one build with Razor of ASP.NET Core, and second using Twig of the Symfony framework. Whether it might be due to the absolute migration from PHP to .NET, because of merging of existing Symfony project into an existing .NET one, or just to reuse existing Razor and Twig templates within your project, in all of the cases, these features can save both time and money.

The application consists of five pages. The index page is defined within the Symfony project's \texttt{GeneralController} class and returns static \texttt{.html} file that is used as a signpost of the application. This can be seen on the following Figure.

\paragraph{Twig rendering} Rendering of a Twig template from a Razor context is provided as seamlessly as possible. The only step the user has to perform is to reference the \texttt{PeachPied.Symfony.AspNetCore.Templating.TwigRenderer} class from the Razor template. This will expose three functions. The \texttt{DataToPhp} support function responsible for handling conversion of the .NET data into the PHP-understandable form. The \texttt{MergePhpArrays} support function that can be further used to merge all the converted data into a single unit. And finally, the \texttt{RenderTwig} function that handles rendering of provided template into a \texttt{string}.


\paragraph{Razor rendering} In order to enable Razor rendering within Twig templates in the Peachpied Symfony project, the user must first add the \texttt{RenderRazorService} service. This is done standardly inside the \texttt{ConfigureServices} method in server's \texttt{Startup} class. The service can be registered as \texttt{transient}, \texttt{scoped} or \texttt{singleton}. It is up to the user to select a lifetime that suits his or her usage of the functionality the best. 

Furthermore, special wrapper around the \texttt{Environment} class in the \texttt{Twig} namespace called the \texttt{RSEnvironment} is provided and can be found in the same namespace. It can be used exactly as Symfony's \texttt{Environment} class and its only difference lays in additional \texttt{render\_razor} function that is accessible within Twig templates rendered with it.

Now, the user can render a Razor template into a \texttt{string} by calling the \texttt{render\_razor} function and providing it with a relative path to the template, and the data that are to be passed to the template's \texttt{ViewBag}. The data provided will be automatically converted into the .NET environment comprehensible form and thus are expected to be supplied in the PHP native form.

\section{Example 2: An application using Twig and Razor template engines without Symfony}
Usage of the Twig template engine within Razor without using any actual Symfony project can be found in the \texttt{Examples/Twig-Razor-Only} application. Once again, the application is stared by running the \noindent\codebox{dotnet run} command from the \texttt{Examples/Twig-Razor-Only} directory. This will start the application again on \texttt{localhost:5004}. The first start-up takes considerably less amount of time than in the previous example because there is no need for any Symfony Components unpacking as there is no Symfony application included. 

This example illustrates how easily can be the Twig rendering feature used from the plain ASP.NET Core application, without any unnecessary bonds to any particular Symfony project. This application uses \texttt{Razor Page} and \texttt{Twig In Razor Page} routes from the previous application, without any further modifications, revealing this feature's actual independence on Symfony. All the Twig templates are stored inside the \texttt{Templates} directory and referenced on the \texttt{RenderTwig} function invocation just as they would if they were stored inside the Symfony project. Previous example's \texttt{index.html} was moved into the \texttt{Server} project and modified in order to satisfy this application's needs. Furthermore, Twig calendar styles were brought into the \texttt{Server} project as well.
